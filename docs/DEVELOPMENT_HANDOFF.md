# 까탈로그 개발 인계

작성일: 2026-10-29 (Asia/Seoul)

## 최신 상태

React 이주와 초대 기반 그룹 지도, 그룹별 비공개 DB·사진 접근, 작성자 전용 편집을 적용했다.
현재 정책과 검증은 `docs/GROUP_CATALOG.md`가 기준이다. 그룹장 특권과 플랫폼 관리자 모드는 없다.
댓글과 의견 집계도 적용했다. 등록자가 메달을 수정하면 기존 표를 초기화하고, 다른 그룹원들의 상승·유지·하락 표는 집계만 한다. 자동 메달 변경·삭제는 종료했다.
아래 내용은 개편 전 인계 기록이며 현재 구현은 `docs/GROUP_CATALOG.md`를 따른다.

## 다음 작업

다른 컴퓨터에서 이 저장소를 열어 React 이주부터 단계별로 진행한다.
첫 단계는 현재 기능과 디자인을 유지하는 React 이주다. 그룹 기능과 새 정책은 후속 단계로 분리한다.
서비스 기획서는 사이트 개편 후 작성한다.

이 문서는 대화에서 정한 개발 방향을 인계한다. 아래의 개편 정책은 아직 구현되지 않았다.

### 2026-10-29 진행 상태

React 이주를 이 세션에서 구현했다. 새 개발 환경에서는 `npm ci` 후 `npm run dev`로 실행한다.
소스는 `outputs/ccatalog/src/`, 정적 파일은 `outputs/ccatalog/public/`, 빌드 결과는 `dist/`다.
로컬 설정의 현재 경로는 `outputs/ccatalog/public/config.json`이다. 기존 설정 파일은 이 경로로 복사해 사용한다.
기존 서비스 기능은 유지하며 그룹, 댓글, 투표와 방문 인증 제거는 후속 단계에 남아 있다.
이하의 기존 구조 설명은 이주 전 기준 기록이며, 현재 구조와 검증 내용은 `docs/REACT_MIGRATION.md`를 참고한다.

## 다른 컴퓨터에서 시작

```sh
git clone https://github.com/mongkwon/ccatalog.git
cd ccatalog
```

클론한 폴더를 Codex 프로젝트로 열고 이 문서와 README를 읽도록 요청한다.
전체 과거 대화가 새 대화에 전달된다고 가정하지 않는다.

로컬 실행에 필요한 `outputs/ccatalog/config.json`은 Git 추적에서 제외돼 있다.
`outputs/ccatalog/config.example.json` 형식에 맞춰 다음 설정을 별도로 준비한다.

- `naverMapKey`: 네이버 지도 클라이언트 키
- `supabaseUrl`: Supabase 프로젝트 URL
- `supabaseAnonKey`: 브라우저용 Supabase 키

비밀 키와 관리자용 키를 문서나 브라우저 코드에 넣지 않는다.
GitHub Actions는 `NAVER_MAP_KEY`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` 저장소 Secrets로 배포용 config를 생성한다.

현재 앱은 정적 서버로 실행한다. Python 3가 설치된 환경의 예:

```sh
python3 -m http.server 4174 --directory outputs/ccatalog
```

접속 주소: http://127.0.0.1:4174/
해당 포트가 사용 중이면 다른 포트를 선택하고 외부 인증 설정도 확인한다.

네이버 지도 허용 URL, Supabase 로그인 Redirect URLs, 카카오 설정은 새 실행 주소에 맞게 확인한다.
네이버 장소 검색에는 `naver-place-search` Edge Function과 서버 측 검색 API 설정도 필요하다.
Supabase 프로젝트 식별자: `hyjkmfmkupegiabiwtld`.
카카오의 Supabase callback 주소: `https://hyjkmfmkupegiabiwtld.supabase.co/auth/v1/callback`.

## 현재 앱의 구조와 이주 시 보존할 동작

`app.js`의 공통 `state`와 수동 `render()`가 핵심 화면을 관리한다.
`render()`는 목록, 결과 개수, 상세 카드, 지도 핀, 독 슬라이더 갱신 함수를 호출한다.
계정 모드 변경은 `setAccountMode()`가 body 클래스, 추가 버튼 접근, 계정 패널 등을 따로 갱신한다.
`NaverMapAdapter`는 SDK 객체를 직접 관리하며 현재 식당 마커를 일괄 재생성한다.

다음 기능과 외관을 React 이주 완료 기준으로 삼는다.

- 현재 지도, 핀, 메달, 목록, 검색/필터와 상세 카드
- 현재 위치 점, 초기 현재 위치 중심과 주변 식당이 보이도록 하는 줌 조정
- 핀/목록 선택 시 하단 카드 위 가시 영역을 고려한 부드러운 지도 이동
- CSS 기반 밝은 유리 스타일, 하단 독, 누름/드래그 확대, 검색/필터 모핑
- 모바일 Safari의 터치 잔상 방지, 키보드, safe-area, 반응형 여백
- 카카오 로그인/로그아웃과 현재 계정 모드별 권한
- 기존 음식점/메뉴 가격/배달 앱/사진/건의/방문/튜토리얼 기능

SVG 굴절 스타일은 과거에 적용 후 Safari 대응 문제로 사이트에서 롤백했다.
React 이주 중에는 현재 CSS 스타일을 유지한다.
기존 방식으로 다시 돌아간 지도 보정 실패 이력이 있으므로 좌표 보정과 애니메이션은 실제 코드와 동작을 먼저 확인한다.

현재 정식 자동화 테스트 스위트는 없다. 이전에는 브라우저 동작 확인과 일부 임시 스크립트로 검증했다.
과거 수동 검증 결과를 새 환경의 테스트 결과로 표현하지 않는다.

## 확정된 개편 정책

### 초대 기반 그룹 지도

- 그룹마다 별도의 맛집 기록을 가진다.
- 가입한 회원 누구나 그룹을 생성할 수 있다.
- 초대 링크로 로그인한 회원이 바로 그룹에 가입한다. 별도 가입 승인은 두지 않는다.
- 그룹 맛집, 메뉴, 사진은 해당 그룹 회원에게만 공개한다. DB 및 Storage 접근 제어도 함께 적용한다.
- 한 회원이 여러 그룹에 참여할 수 있는 방향으로 진행한다.
- 같은 음식점이 여러 그룹에 있으면 하나의 지도 핀에서 그룹별 기록과 메달을 확인한다.
- 기존 맛집은 사용자가 그룹장인 첫 그룹으로 이전한다. 이전 전 사용자 계정 식별을 확인한다.

### 메달과 의견

- 등급은 동메달/은메달/금메달을 유지한다.
- 최초 등록자의 메달을 해당 그룹 식당의 초기 평가로 삼는다.
- 나중에 같은 식당을 등록하려는 경우 기존 평가를 즉시 덮어쓰지 않는다.
- 그룹원은 댓글/의견과 상승/유지/하락 투표로 참여한다.
- 전체 그룹원 과반이 상승 또는 하락을 선택하면 메달을 한 단계 변경한다.
- 동메달에서 하락이 결정되면 그 그룹 지도에서 식당을 제외한다.
- 해당 식당을 가진 다른 그룹의 기록은 유지한다.

### 제거할 기존 기능

- 위치 기반 방문 인증
- 현장 메달 동의에 따른 방문 집계
- 서로 다른 식당 3곳 방문 후 까탈리스트 승급

React 이주 단계에서는 기존 동작을 보존하고, 그룹 정책 적용 단계에서 제거한다.
과거 방문 데이터의 보관/삭제 방식은 별도 확정 후 마이그레이션한다.

## 구현 전에 확인할 정책

아래 항목은 대화에서 제안됐거나 사용자가 검토 중인 내용이다. 확정 정책으로 구현하지 않는다.

1. 회원 역할: 초기에는 그룹장을 까탈리스트로 정했으며, 이후 모든 그룹원이 까탈리스트가 되어 공동 등록하는 방향을 논의했다. 공동 등록 의도는 확인되지만 명칭과 최종 권한은 확정이 필요하다.
2. 수정/삭제/사진 권한: 자기 기록만 관리할지, 그룹장이 전체 관리할지, 그룹 전체가 편집할지 결정한다.
3. 여러 그룹 지도 표시: 모든 참여 그룹을 한 지도에 표시하고 그룹별 색상/필터를 두는 안을 사용자가 제안했다. 기본 표시 방식과 필터는 확정이 필요하다.
4. 투표 주기: 메달 변경 후 기존 표를 종료하고 새 라운드를 여는 안이 제안됐다. 중복 적용 방지, 표 변경/취소, 유지 과반 처리와 만료 방식을 정한다.
5. 투표 분모: 가입/탈퇴 시 전체 그룹원 수를 언제 계산할지, 등록자도 투표할지 정한다. 그룹원 1명일 때 동작도 정한다.
6. 금메달 상승: 최상 등급에서 상승 버튼과 표를 어떻게 처리할지 정한다.
7. 식당 제외: 댓글/투표 이력을 보관할지, 재등록을 허용할지 정한다.
8. 그룹 운영: 초대 링크 만료/재발급, 내보내기, 탈퇴, 그룹장 위임/삭제 규칙을 정한다.
9. 장소 중복 식별: 그룹 안과 그룹 사이에서 같은 식당임을 판단할 장소 ID 및 지점 구분 기준을 정한다.
10. 기존 플랫폼 관리자: 그룹장 권한과 별개로 유지할 운영 권한 범위를 정한다.

## 단계별 작업 순서

### 1. React 이주

- 권장 시작점은 React + Vite. 확정 의존성 버전은 실제 착수 시 확인한다.
- 별도 작업 브랜치에서 진행하고 main 배포는 현재 서비스로 유지한다.
- 현재 코드의 동작을 읽고 컴포넌트, 상태, 데이터 접근, 지도 어댑터 경계를 정한다.
- 기존 CSS와 시각 자산을 재사용한다.
- 지도 SDK 생성/이벤트/정리를 React 생명주기와 연결한다. 마커 갱신 전략은 명시적으로 관리한다.
- 기존 config 로딩과 인증 복귀 경로, Pages `/ccatalog/` 기본 경로를 보존한다.
- 빌드 결과 디렉터리와 GitHub Actions 배포 경로를 함께 맞춘다.
- 주요 사용 흐름과 PC/모바일 화면을 검증하고 검토 후 배포한다.
- 이 단계에서 그룹 DB, 투표, 댓글을 동시에 추가하지 않는다.

### 2. 그룹과 비공개 접근

- 미확정 역할/초대 정책을 먼저 확인한다.
- 그룹, 회원 관계, 초대, 식당 소속 모델과 RLS/Storage 정책을 설계한다.
- 기존 음식점을 첫 그룹으로 안전하게 이전한다.
- 그룹 생성/초대 가입/목록과 지도 표시를 구현한다.
- 타 그룹 데이터가 회원에게 노출되지 않는지 확인한다.

### 3. 공동 등록과 의견

- 확정 권한에 맞춰 등록/수정/삭제/사진 기능을 연결한다.
- 같은 식당의 중복과 여러 그룹 소속을 처리한다.
- 최초 메달 유지, 작성자 표시, 댓글/의견을 구현한다.
- 방문 인증/기존 승급/기존 건의 심사 UI를 새 정책에 맞게 정리한다.

### 4. 메달 투표

- 투표 라운드와 전체 그룹원 과반 정책을 확정한다.
- 서버에서 중복 투표, 동시 요청, 메달 변경을 일관되게 처리한다.
- 동메달 하락 시 해당 그룹 기록을 지도에서 제외한다.
- 작은 그룹, 가입/탈퇴, 금메달, 재등록 등 경계 상황을 검증한다.

### 5. 마무리 및 기획서

- 실제 구현과 정책에 맞춰 튜토리얼, 계정 문구, README를 갱신한다.
- 주요 기능과 그룹 간 접근 제어를 종합 검증한다.
- 사용자가 만든 배경/대상/기준을 질문으로 보완해 기획서를 작성한다.
