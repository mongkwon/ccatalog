## 사용자가 결정한 편집 방향

- 서비스 기획 중심으로 구성하고 기술 선택 근거와 구현을 고려한 설계도 포함한다.
- 개인 프로젝트로 표기하고 별도 ‘담당 역할’ 항목은 만들지 않는다.
- ‘AI와 협업’을 전면에 내세우지 않는다. 실제 도구 활용 범위를 질문받으면 정확하게 설명한다.
- 서비스 정책을 전환한 이유와 과정은 개선 사례로 제시한다.
- React 선정 이유는 선언적 렌더링, 단방향 데이터 흐름, reconciliation, Effect 수명 주기, 명령형 SDK 연동 등 정확한 개발 용어로 간결하게 쓴다.
- 기술 설명의 분량을 늘려 모호함을 덮지 않는다. 실제 구현과 연결된 용어와 근거를 사용한다.
- 초기 Vanilla JavaScript 구현과 React 이주 이력은 유지한다. 처음부터 React를 선택했다고 서술하지 않는다.
- 반복적으로 구현·사용·개선한 과정은 설명하되, 확인되지 않은 스프린트·백로그 운영을 주장하지 않는다.
- 사용자 인터뷰·실험·성과 수치·성능 개선을 만들어내지 않는다. 개인 경험, 가설, 구현 사실, 검증 결과를 구분한다.
- 기존 지도 서비스의 제약은 기획자의 경험으로 서술한다. 최신 서비스 전체의 기능을 조사한 결과로 표현하지 않는다.
- 불필요한 ‘~가 아니라 ~다’, ‘~보다는 ~다’ 대조 문장을 피한다.

## Figma 제작 계획

### 형식과 시각 방향

- 편집 가능한 Figma Design 파일, 16:9 가로형 프레임 약 10장.
- 흰 배경과 검은 본문을 중심으로 읽기 쉽게 편집한다.
- 앱의 유리 효과는 제품 화면에서 보여준다. 본문 전체에 장식 효과를 확대하지 않는다.
- 장마다 핵심 주장 하나를 배치하고 필요하면 기술 보충 페이지를 추가한다.
- 화면과 도식의 텍스트·요소는 가능한 한 편집 가능한 레이어로 구성한다.
- 실제 화면 사용 시 개인정보와 비공개 그룹 정보의 노출 범위를 확인한다. 가상의 예시는 예시로 표시한다.
- 서비스·GitHub 링크는 PDF에서도 클릭할 수 있도록 설정한다.
